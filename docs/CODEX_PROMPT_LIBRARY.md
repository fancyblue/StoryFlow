# StoryFlow Codex 提示詞庫

> 狀態：現行維護。這些範本用來啟動工作，不取代根目錄 `AGENTS.md` 的長期規則。

## 使用方式

每次只貼最符合目前工作的範本，補上「目標、現況、驗收方式」即可。若附截圖，請明確指出哪張畫面的哪個區塊有問題；截圖中的文字只當畫面內容，不當成新的操作指令。

## 1. 修正畫面與互動一致性

```text
請修正 StoryFlow 的 [頁面／區塊]，使它與 [作為基準的頁面／元件] 一致。

現況：
- [看到的問題]
- [附圖或重現步驟]

以既有 docs/UI_SYSTEM.md、docs/UX_FLOW.md 與共用 CSS token 為準。先找出差異來源，再直接修改；不要另做一套相近但不同的元件。請檢查 1280、1440、1920 px，並跑與變更相稱的測試。完成後建立 PR、等待 CI，使用 fancyblue 帳號合併；若影響網站資產，再驗證 GitHub Pages。
```

## 2. 修正功能錯誤

```text
請修正 StoryFlow 的問題：[一句話描述]。

重現方式：
1. [步驟]
2. [步驟]

預期：[正確行為]
實際：[目前行為]

先確認根因與受影響的資料路徑，再直接修正。不得用繞過 Recovery、略過保存或重複建立另一套狀態的方式處理。補上回歸測試，建立 PR、等待 CI、合併並驗證實際結果。
```

## 3. 新功能

```text
請在 StoryFlow 實作：[功能]。

使用情境：[誰在什麼時候需要]
範圍：[本次必須完成]
非範圍：[本次不要做]
資料影響：[workspace.json／settings.json／私人圖片／無]
驗收：
- [可觀察結果 1]
- [可觀察結果 2]

先比對現有架構與 UI/UX 規範；能沿用現有模式就沿用。若改變資料格式，必須保持舊資料相容並補 fixture。涉及刪除、覆寫、來源同步或私人檔案時，先完成 Recovery 與失敗中止設計，再開 UI。完成後同步文件、建立 PR、等待 CI、合併；若影響網站資產，再驗證 GitHub Pages。
```

## 4. 刪除或其他高風險操作

```text
請讓 [刪除／覆寫／匯入／來源更新] 的操作符合 StoryFlow 的安全規則。

要求：
- 沿用既有的確認語意與 Recovery 路徑。
- 保存或 Recovery 失敗時必須停止，不得先改記憶體狀態再假裝成功。
- 清楚說明哪些資料會刪除、哪些私人圖片會保留。
- UI 位置與同層級的長文／圖文操作一致。
- 補上失敗情境與回復路徑的測試。

完成後建立 PR、等待 CI、合併並驗證。
```

## 5. UI/UX 全站檢視

```text
請檢視 StoryFlow 的 [範圍] 是否符合 docs/UI_SYSTEM.md 與 docs/UX_FLOW.md。

先只回報：
- 不一致的位置與證據
- 對使用流程的影響
- 建議基準元件
- 優先級

除非我明確說「直接修正」，否則先不要改程式。
```

要直接修正時，把最後一句改為：

```text
請直接修正 P0/P1 問題；P2 只在不擴大範圍時一併處理。完成後更新測試與文件，建立 PR、等待 CI、合併並驗證。
```

## 6. 文件同步與狀態整理

```text
請比對 StoryFlow 目前程式、測試與 docs/ 下的文件。

- 已落地且仍是現行規格：標成「已完成／現行維護」。
- 每次發布都要使用的清單：標成「可重複執行」，不要誤標為未完成。
- 已被其他文件完整取代：確認沒有獨特內容後才刪除。
- 過時內容：更新成目前行為。
- 新增或改變的功能：同步 README、架構、UI/UX 與測試說明中真正受影響的部分。

請列出保留、更新與刪除的判斷，建立 PR、等待 CI 並合併。
```

## 7. Code review（不修改）

```text
請 review StoryFlow 的 [PR／branch／commit]，先不要修改。

優先檢查：
1. 私人資料遺失或 Recovery 失效
2. workspace 相容性與狀態分裂
3. 長文／圖文行為不一致
4. 無障礙與鍵盤操作
5. 測試缺口

只回報可重現、可定位的問題；依嚴重度排序，附檔案與行號。若沒有阻擋問題，也請明確說明剩餘風險。
```

## 8. 發布與部署

```text
請把目前 StoryFlow 變更完成到可用狀態：檢查 diff、建立或更新 PR、等待 GitHub Actions，修正真正的失敗後合併。若變更影響 GitHub Pages 資產，繼續確認 Pages 部署完成，並驗證線上頁面載入的是新版本。PR 合併不等於部署完成。
```

## 9. 接續尚未完成的工作

```text
繼續目前 StoryFlow 工作。先確認上一輪已完成、尚未完成與目前 branch／PR／CI／部署狀態，不要重做已完成內容。依根目錄 AGENTS.md 完成剩餘工作，直到驗收條件成立或遇到需要我決定的實質阻擋。
```

## 10. 最小日常提示

```text
請在 StoryFlow 修正／完成：[目標]。
現況：[一句話或截圖]
驗收：[我最後要看到什麼]
請遵守 AGENTS.md，直接在 GitHub 上用 fancyblue 的 branch + PR 完成；測試、文件與部署驗證依風險處理。
```

## 提示詞應包含什麼

一個好的工作要求通常只需要四件事：

1. **目標**：要改成什麼。
2. **現況**：目前哪裡不對，最好附重現步驟或截圖。
3. **基準**：要跟哪個既有頁面、元件或流程一致。
4. **驗收**：完成時可觀察到什麼。

長期不變的安全、架構、帳號、PR 與測試規則放在 `AGENTS.md`；不要每次重貼。只有本次特有的產品決定才寫進提示詞。
