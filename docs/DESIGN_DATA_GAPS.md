# 介面重新設計：資料結構缺口

> 狀態：**候選／待驗證** — 尚未授權實作。這份文件只記錄「介面設計過程中提出、但目前資料模型沒有」的需求，
> 供實作前逐項確認要不要做。任何一項在動工前都需要重新確認，不得因為它列在這裡就視為已核可。

介面提案本身不在 repo 內，是一份設計稿；這份文件只保留會影響 `content-model.js` 結構或既有行為的部分。

## 一、分平台覆寫的範圍

目前 `normalizeVisualEntry` / `normalizePublishItem`（`src/projects/content-model.js`）已支援兩個分平台欄位：

| 欄位 | 現況 | 備註 |
| --- | --- | --- |
| `platformTitles` | 已支援 | 每個平台可有自己的標題 |
| `platformHashtags` | 已支援 | 以 `keepEmpty: true` 正規化，所以「刻意不加標籤」與「沿用共用標籤」是兩種狀態 |

設計過程提出、但目前**沒有**的：

### 1. 分平台的「附上後記」開關

- 現況：`includeAfterword` 是單一 boolean（`content-model.js:97`、`publishing-flow.js:53`），一次決定所有平台。
- 需求：不同平台可各自決定要不要附後記。
- 影響：需要新增 `platformIncludeAfterword`（boolean record），並讓 `outputSections(part, platform, includeAfterword)` 依平台取值。
- 待確認：共用值與平台值的優先順序，以及是否需要像 hashtags 一樣的「刻意關閉」第三態。

### 2. 分平台的「複製時附上標題」開關

- 現況：平台預覽對話框的複製標題選項是單一設定，不隨平台保存。
- 需求：每個平台各自決定複製內容時要不要帶標題。
- 影響：需要 `platformCopyTitle`（boolean record），並與既有的 `outputWithTitle(part, platform, includeAfterword, titleStyle)` 串接。

### 3. 分平台的摘要

- 現況：`summary` 是單一字串（`content-model.js:92`），沒有 `platformSummaries`。
- 需求：不同平台可以有不同的摘要／描述。
- 影響：需要新增 `platformSummaries`（string record）。這是資料模型變更，不是介面問題——介面設計稿刻意沒有畫這個欄位。
- 待確認：是否所有平台都需要，或只有圖文模式需要。

## 二、發布佇列的排序

### 4. 「最新確認」的排序（已查證：文案與實作相符，不需要修）

**先前這一節寫「文案與實作不符」，那是誤判**，記錄更正以免又照著改壞：

- `publishing-flow.js:189` 的 `updatedAt || createdAt` 排序在
  `if (state.contentMode === VISUAL)` 的提前返回分支裡，**只管圖文**，而圖文的文案正是
  「最近編輯的圖文顯示在最上面」——相符。
- 長文走的是另一段（`publishing-flow.js:195-203`）：章節由後往前、章節內的篇也由後往前，
  **完全不看時間戳**。篇由 `chapter.parts.push(part)`（`src/core/app.js:346`）依確認順序追加，
  所以反向走就是最新確認的在最上面——文案「最新確認的文章顯示在最上面」也相符。
- 先前聲稱的症狀「改後記會讓文章跳到最上面」對長文**不成立**，長文的順序根本不受 `updatedAt` 影響。

真正存在的是一個邊界情況，但不是 bug：排序是「章節的文件順序」而非全域確認時間，
所以**回頭去切一個較早的章節**時，那些新確認的篇會排在較後章節的篇下面。
正常連載（章節依序新增、依序切篇）不會遇到。

若哪天要讓排序變成全域的確認時間，才需要新增 `confirmedAt`，在「確認並存成 Markdown」時寫入。
那是為了處理上述邊界情況的**增強**，不是修正。

### 5. ~~排序偏好可選~~ · 已實作，**不需要資料模型變更**

原本記的待確認是「歸在哪一層：全域偏好或每個作品各自」。實作時查證後，這一項比原本寫的單純，
但也多了一個原本沒記的**依賴**：

- **長文的篇沒有任何時間戳記。** `src/core/app.js:339` 建立的 part 只有
  `id`／`title`／`startBlock`／`chars`／`platformStatus` 等等——沒有 `createdAt`、
  沒有 `updatedAt`、沒有 `confirmedAt`。只有圖文的 entry 有時間戳記。
- 所以「最近更新」對長文**做不到**，除非先做第 4 項的 `confirmedAt`。
  **第 5 項對長文是依賴第 4 項的**，原本沒記這個依賴。
- 實際做的是不依賴時間戳記的版本：**「章節順序」（文件正序）與「最新在前」（文件倒序，現況）**。
  兩者都只是同一份文件順序的兩個方向，零資料模型變更。真正的「跨章節確認時間」排序
  只有在回頭去切較早的章節時才有差別——那正是第 4 項描述過、並判定為增強而非修正的邊界情況。
- **存在哪一層：全域。** `switchProject()` 早就有「跨作品帶過去」的慣例
  （切篇字數上下限、場景分隔符、排版格式），排序是同一類的工作習慣，
  所以加進同一份清單。實作時把那份清單抽成 `CARRIED_PREFERENCES` 一處——
  它原本在三個地方各寫一遍，而我加的第五個偏好只進到其中一個。
- **圖文不提供這個控制**：沒有章節可排，而且它的 entry 確實有 `updatedAt`，
  順序是固定的，原本那句說明保留。

## 三、作品清單的進度

### 6. 「未切」的計算方式

- 需求：作品列要顯示「另有 N 章未切」，章節列要顯示「剩 N 字未切」，而「繼續切篇」要能指向最新那一個還沒切的章。
- 現況：發布進度可由 `chapter.parts` 與 `platformStatus` 推導。「未切」需要確認能否由既有資料推導（章節總字數扣掉已建立篇的字數），或需要另外保存。
- 待確認：
  - 手動建立的章節、以及來源已變更但尚未重新切篇的章節，這個數字要怎麼算才不會誤導。
  - 「最新那一個還沒切的章」的定義：是章節順序上第一個沒有 parts 的，還是最後一個？連載往後長，兩者在中間有缺口時會給出不同答案。

### 來源掛在哪一層（已查證，非待確認）

設計初稿曾寫「作品全部切完時，主要動作改為更新來源」。那是錯的，記錄原因以免再犯：

- 來源綁在**章節**：`chapter.source = { id, tabId, tabTitle, name }`，指一個 Google Docs 文件的一個分頁。
- `project.sourceDocId` 不是作品自己的屬性，是推導值——`deriveSourceDocId()`（`src/projects/projects.js:47`）
  只取**第一個**有 `source.id` 的章節。所以作品列顯示「來源 Google Docs」在混用的作品上會誤導。
- 一個作品可以同時擁有多個分頁的章節與手動章節。`renderChapters()`
  （`src/ui/workspace-interactions.js:304`）就是依 `docId::tabId` 把章節分組，沒有來源的歸「手動章節」。
- 「更新來源」是章節層的動作：`source-flow.js:580` 的提示寫「請選擇該章節後使用『更新來源』」。

因此：作品層沒有「那一個來源」可以更新，`更新來源` 不得出現在作品列；作品列也不再宣稱單一來源，
改由章節列的副標寫出各自的檔案與分頁。
